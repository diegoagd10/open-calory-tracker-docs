El recorrido

Quién hace qué

Registrar una aplicación y autorizarla son acciones distintas. Pueden hacerlas personas diferentes.

01

Quien desarrolla la app

En Settings → OAuth clients registra el nombre, tipo y URI de retorno. Recibe el client_id. En un cliente confidencial recibe además un secreto que se muestra una sola vez.

02

Dueño del Food Log

Abre la solicitud de autorización en su navegador, inicia sesión y marca el permiso daily-log:read. Puede permitirlo o rechazarlo.

03

La aplicación

Recibe la redirección en su callback, valida state, intercambia el código por tokens y llama a la API con Authorization: Bearer.

El Client ID identifica la aplicación, no al usuario. El token identifica la conexión aprobada y determina qué Food Log se lee. Registrar un cliente no concede acceso por sí solo.

Paso 1

Registra tu aplicación

Entra a tu instancia, abre Settings → OAuth clients y selecciona Register a client.

Elige el tipo correcto

Público

CLI, móvil o app en el navegador

El código se distribuye a usuarios o corre en su dispositivo. No puede guardar un secreto compartido. Usa Client ID + PKCE.

Confidencial

Servidor que controla tu equipo

Puede guardar el secreto en el servidor. Usa Client ID + PKCE + autenticación Basic en el token endpoint. Nunca envíes el secreto al navegador.

Datos que debes preparar

Nombre
El nombre que verá el usuario al autorizar.
Redirect URI
La URL de tu callback, por ejemplo https://mi-app.example/oauth/callback.
Permiso disponible
daily-log:read — consulta únicamente.

Guarda el Client ID que muestra la confirmación. Si elegiste confidencial, copia también el Client Secret en ese momento: después no se vuelve a mostrar.

Puedes registrar de 1 a 10 URI de retorno, una por línea. Deben usar HTTPS; HTTP se permite solo con localhost, 127.0.0.1 o [::1]. La solicitud OAuth debe usar exactamente una URI guardada en el registro. Para producción, publica la instancia y el callback mediante HTTPS confiable.

Pasos 2–4

Integra el flujo OAuth

Los ejemplos usan un cliente público de línea de comandos con callback local. En un cliente confidencial, añade el secreto solo en el servidor.

2

Prepara PKCE y redirige al navegador

Genera un code_verifier y un state nuevos para cada intento. Conserva ambos asociados a la sesión hasta que vuelva el callback. Descubre las URLs oficiales de tu instancia en /.well-known/oauth-authorization-server.

JavaScript · construir la URL de autorización
import { randomBytes, createHash } from "node:crypto";

function startAuthorization(instanceUrl, clientId, redirectUri) {
  const verifier = randomBytes(32).toString("base64url");
  const state = randomBytes(24).toString("base64url");
  const challenge = createHash("sha256")
    .update(verifier, "ascii").digest("base64url");
  const url = new URL("/oauth/authorize", instanceUrl);
  url.search = new URLSearchParams({
    response_type: "code",
    client_id: clientId,
    redirect_uri: redirectUri,
    scope: "daily-log:read",
    code_challenge: challenge,
    code_challenge_method: "S256",
    state,
  }).toString();
  return { authorizationUrl: url.toString(), verifier, state };
}

// Guarda verifier y state en la sesión; abre authorizationUrl
// en el navegador del dueño del Food Log.
3

Procesa el callback

Tras iniciar sesión y aceptar el permiso, el navegador vuelve a tu redirect_uri con code y state. Comprueba que state coincide con el guardado antes de usar el código. Si la persona declina, recibirás error=access_denied. El código dura cinco minutos y se usa una sola vez.

Ejemplo de respuesta al callback
http://127.0.0.1:4567/callback?code=CODIGO&state=STATE
4

Intercambia el código por tokens

Envía el mismo redirect_uri y el code_verifier original. Un cliente público no manda secret; un cliente confidencial añade Authorization: Basic base64(client_id:client_secret) desde su servidor.

Cliente público · POST /oauth/token
curl -X POST "https://calory.example/oauth/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data-urlencode "grant_type=authorization_code" \
  --data-urlencode "client_id=TU_CLIENT_ID" \
  --data-urlencode "code=CODIGO_DEL_CALLBACK" \
  --data-urlencode "redirect_uri=http://127.0.0.1:4567/callback" \
  --data-urlencode "code_verifier=VERIFIER_GUARDADO"

La respuesta incluye access_token, refresh_token, token_type: "Bearer", scope: "daily-log:read" y expires_in: 900 (15 minutos).

5

Lee un día del Food Log

La fecha tiene formato YYYY-MM-DD. No pases un User ID: el servidor elige la cuenta asociada al token.

GET /api/v1/daily-log
curl "https://calory.example/api/v1/daily-log?date=2026-09-27" \
  -H "Authorization: Bearer TU_ACCESS_TOKEN"

Recibirás JSON con entradas de comida, agua, objetivos y totales nutricionales. La API v1 es de solo lectura.

Referencia rápida

Mantén la conexión bajo control

Renovar

Cuando caduque el access token, envía grant_type=refresh_token, client_id y el refresh token vigente a POST /oauth/token. El cliente confidencial vuelve a usar Basic. Guarda el nuevo refresh token de forma atómica: cada uno se usa una sola vez.

Revocar

El dueño del Food Log puede abrir Settings → OAuth clients y revocar una conexión. Sus access y refresh tokens dejan de funcionar de inmediato; las demás conexiones no cambian.

Proteger credenciales

Conserva tokens y secretos fuera de URLs, repositorios y registros. Usa HTTPS para la instancia y el callback externo. Un Client Secret nunca sustituye el permiso del usuario ni un Bearer token.
