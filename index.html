Food Log API · v1

Connect your app to the Food Log.

Register your client, ask the Food Log owner for permission, and read one day of data with OAuth 2.0. The owner decides whether to grant access and can revoke it at any time.

The flow

Who does what

Registering an app and authorizing it are separate actions. Different people can perform them.

01

App developer

In Settings → OAuth clients, register the name, type, and redirect URI. You receive a client_id. A confidential client also receives a secret shown only once.

02

Food Log owner

Opens the authorization request in their browser, signs in, and selects the daily-log:read permission. They can allow or decline.

03

The application

Receives the redirect at its callback, validates state, exchanges the code for tokens, and calls the API with Authorization: Bearer.

The Client ID identifies the application, not the user. The token identifies the approved connection and determines which Food Log is read. Registration alone does not grant access.

Step 1

Register your application

Sign in to your instance, open Settings → OAuth clients, and select Register a client.

Choose the right client type

Public

CLI, mobile, or browser app

Its code runs on a user's device or is distributed to users. It cannot keep a shared secret. Use Client ID + PKCE.

Confidential

Server you control

It can keep the secret on the server. Use Client ID + PKCE + Basic authentication at the token endpoint. Never send the secret to the browser.

Details to prepare

Name
The name the owner sees when authorizing.
Redirect URI
Your callback URL, for example https://my-app.example/oauth/callback.
Available permission
daily-log:read — read-only access.

Save the Client ID shown on the confirmation page. If you chose a confidential client, copy the Client Secret now: it will not be shown again.

You can register 1 to 10 redirect URIs, one per line. They must use HTTPS; HTTP is allowed only for localhost, 127.0.0.1 or [::1]. The OAuth request must use a URI saved in the registration exactly. In production, serve the instance and callback over trusted HTTPS.

Steps 2–5

Integrate the OAuth flow

These examples use a public command-line client with a local callback. For a confidential client, add the secret only on the server.

2

Prepare PKCE and open the browser

Generate a fresh code_verifier and state for each attempt. Store both with the session until the callback returns. Discover your instance's official URLs at /.well-known/oauth-authorization-server.

JavaScript · build the authorization URL
import { randomBytes, createHash } from "node:crypto";

function startAuthorization(instanceUrl, clientId, redirectUri) {
  const verifier = randomBytes(32).toString("base64url");
  const state = randomBytes(24).toString("base64url");
  const challenge = createHash("sha256")
    .update(verifier, "ascii").digest("base64url");
  const url = new URL("/oauth/authorize", instanceUrl);
  url.search = new URLSearchParams({
    response_type: "code",
    client_id: clientId,
    redirect_uri: redirectUri,
    scope: "daily-log:read",
    code_challenge: challenge,
    code_challenge_method: "S256",
    state,
  }).toString();
  return { authorizationUrl: url.toString(), verifier, state };
}

// Store verifier and state with the session. Open authorizationUrl
// in the Food Log owner's browser.
3

Handle the callback

After sign-in and approval, the browser returns to your redirect_uri with code and state. Check that state matches the stored value before using the code. If the owner declines, you receive error=access_denied. The code expires after five minutes and can be used only once.

Example callback URL
http://127.0.0.1:4567/callback?code=CODE&state=STATE
4

Exchange the code for tokens

Send the same redirect_uri and the original code_verifier. A public client sends no secret; a confidential client also sends Authorization: Basic base64(client_id:client_secret) from its server.

Public client · POST /oauth/token
curl -X POST "https://calory.example/oauth/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data-urlencode "grant_type=authorization_code" \
  --data-urlencode "client_id=YOUR_CLIENT_ID" \
  --data-urlencode "code=CODE_FROM_CALLBACK" \
  --data-urlencode "redirect_uri=http://127.0.0.1:4567/callback" \
  --data-urlencode "code_verifier=SAVED_VERIFIER"

The response includes access_token, refresh_token, token_type: "Bearer", scope: "daily-log:read" and expires_in: 900 (15 minutes).

5

Read a day of the Food Log

The date uses YYYY-MM-DD. Do not pass a User ID: the server selects the account associated with the token.

GET /api/v1/daily-log
curl "https://calory.example/api/v1/daily-log?date=2026-09-27" \
  -H "Authorization: Bearer YOUR_ACCESS_TOKEN"

The JSON response includes food entries, water, goals, and nutrition totals. API v1 is read-only.

Quick reference

Manage the connection

Refresh

When the access token expires, send grant_type=refresh_token, client_id, and the current refresh token to POST /oauth/token. A confidential client uses Basic again. Store the new refresh token atomically: each refresh token can be used only once.

Revoke

The Food Log owner can open Settings → OAuth clients and revoke a connection. Its access and refresh tokens stop working immediately; other connections are unaffected.

Protect credentials

Keep tokens and secrets out of URLs, repositories, and logs. Use HTTPS for the instance and external callback. A Client Secret never replaces the owner's permission or a Bearer token.
